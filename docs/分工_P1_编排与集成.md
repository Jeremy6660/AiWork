## 三、各阶段怎样才算完成

### S0：主数据流与接口样例

要做：

- 画清 `检索 → 画像 → 生成 → 审核 → 评估` 的调用顺序。
- 写出 `orchestrator.run()` 的完整输入与返回 JSON。
- 标明审核失败后如何回到生成，以及最多重试几次。

通过标准：

- P2 能只看流程图说出每个 Agent 的输入和输出。
- P4 提供的黄金场景能完整代入 `run()` 样例。
- 流程图与 `docs/接口约定.md` 字段完全一致。

### S1：检索与画像 stub

要做：

- `search_knowledge()` 返回至少 2 条带来源的假知识。
- `build_profile()` 返回岗位和 6–8 个技能掌握度。
- 各准备一个正常输入和一个异常输入。

通过标准：

- P3 可直接导入两个函数，不需要修改函数名或参数。
- 空问题、未知岗位不会让程序崩溃。
- P1 同时负责验收 P3 的 orchestrator：必须能触发一次审核失败后的重试。

### S2：黄金场景真实数据

要做：

- 只聚焦数控机床操作，收集至少 30 条知识。
- 每条使用统一字段：`id、内容、来源、类型、关键词、采集日期`。
- 至少抽查 10 条来源，记录能否定位到原文。

通过标准：

- P4 能根据“来源”字段独立找到原文位置。
- 不收录无法说明出处的知识。
- P1 验收 P2 的真实检索：覆盖问题有结果，未覆盖问题明确拒答。

### S3：L2 知识锚定

要做：

- 将培训正文拆成可检查的事实断言。
- 对每条断言标记“有依据、无依据、与依据矛盾”。
- 计算事实错误率、无依据陈述率、可溯源率和最终幻觉分数。
- 输出具体修改建议，指出句子、错误和依据来源。

通过标准：

- 手工放入一个错误数值时必须检出。
- 幻觉分数由核查结果计算，不能写死。
- P2 能用固定样例重复得到结构一致的结果。
- P1 验收 P4 的 L1：来源、格式、长度、不确定措辞检查均有单测。

### S4：学习路径与难度交互

要做：

- 根据技能掌握度和先修关系推荐下一项学习内容。
- 掌握度低时生成入门教程，中等时生成实操指南，高时生成进阶挑战。
- 支持“降维解释”和“进阶挑战”两种重生成意图。

通过标准：

- 三种画像得到不同的学习路径和资源类型。
- 推荐理由能说明当前掌握度与先修条件。
- P3 能在不改 UI 数据结构的情况下调用。
- P1 验收 P3 的 L3：任一模型超时，系统仍能降级完成。

### S5：正式界面与可视化

要做：

- 展示知识盲区、难度匹配曲线和学习路径图。
- 展示每个 Agent 的输入摘要、输出摘要、耗时和审核决策。
- 保留一键运行的黄金场景。

通过标准：

- P4 能按演示脚本在 3 分钟内完成主流程。
- 页面能解释“为什么检索这些知识、为什么生成这种难度、为什么通过或驳回”。
- P1 验收 P2 的评测结果：所有数字能追溯到脚本和原始记录。

### S6：代码冻结与部署

要做：

- 打出发布候选版本，不再新增功能。
- 在没有本地缓存的干净环境中完成安装和启动。
- 记录 Python 版本、依赖安装、环境变量和运行命令。

通过标准：

- P2 能只看部署说明从零启动系统。
- 缺少 API key 时给出明确提示，不暴露任何真实密钥。
- P1 验收 P4 的最终视频：10 分钟以内，主链路、差异化和审核闭环完整。

## 四、P1 每日检查

- 当日任务是否能在一天内完成；不能就继续拆分。
- 是否已经把半成品交给验收者运行。
- 正常样例和失败样例是否都保存。
- 是否改动了接口；若改动，契约是否先更新。
- 自己负责验收的任务是否在本机真实复现，而不是只看截图。

## 五、P1 不再长期负责

P1 不再永久承包 Orchestrator、Streamlit、合并、部署和视频。阶段表之外的工作，必须由全组重新安排，不能默认全部交给 P1。
