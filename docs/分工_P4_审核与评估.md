# P4 阶段制任务书

> P4 现在只是成员编号，不再等于“审核与评估负责人”。
> P4 会随阶段轮换场景设计、界面、生成、规则审核、实验和视频任务。
> 总计划与阶段退出门槛以 `阶段制分工与互验计划.md` 为准。

## 一、开始前先读

1. `docs/项目背景.md`
2. `docs/接口约定.md`
3. `docs/阶段制分工与互验计划.md`

P4 的演示和材料任务同样属于正式交付，不等于“只做文档”；必须能运行、解释并验收对应代码链路。

## 三、各阶段怎样才算完成

### S0：黄金场景

要做：

- 将首条真实链路限定为“数控机床操作”。
- 选 3–5 个可由权威资料支撑的问题。
- 准备低、中、高三个学习者画像输入。
- 列出拟使用资料和可访问位置。

通过标准：

- P1 能把问题和画像完整代入 `run()` 样例。
- 问题范围一周内能够完成，不依赖大规模数据。
- P4 验收 P3 的接口样例，确保正常和异常路径都覆盖。

### S1：最简 Streamlit 页面

要做：

- 提供岗位、问题和答题记录输入。
- 只调用 `orchestrator.run()`，不直接调用各 Agent。
- 展示画像、知识、培训内容、审核、评估和协同日志。

通过标准：

- P2 执行 `streamlit run app.py` 后能走完假数据全链路。
- 页面重跑时不会丢失本次结果。
- P4 验收 P2 的生成、审核、评估 stub，字段必须完整。

### S2：受约束的内容生成

要做：

- 生成内容只能依据本次传入的知识列表。
- 根据画像选择教程、实操指南或进阶项目。
- 输出标题、Markdown 正文和引用来源。
- 校验引用来源必须属于知识列表。

通过标准：

- P3 使用三种画像生成的内容有明显难度差异。
- 空知识列表时拒绝生成事实性教程。
- 引用不存在的来源时必须被拦截。
- P4 验收 P1 的知识数据，随机抽 10 条可定位原文。

### S3：L1 规则检查

要做：

- 检查引用来源是否真实存在于知识列表。
- 检查正文是否为空、过短或乱码。
- 检查“可能、大概、据我所知”等不确定措辞。
- 返回具体错误列表和 pass/fail。

通过标准：

- P1 能通过单元样例逐项触发每条规则。
- 规则结果不依赖外部 API。
- 错误信息能被 orchestrator 直接转为修改建议。
- P4 验收 P3 的审核页面，确保前后差异和失败原因可见。

### S4：对比和消融实验

要做：

- 比较单次大提示词与多 Agent 链路。
- 比较低、中、高画像对同一问题的生成结果。
- 比较无审核、L1+L2、L1+L2+L3 三种配置。
- 保存输入、配置、原始输出、耗时和指标。

通过标准：

- P2 能使用同一脚本重新运行实验。
- 失败结果和不利结果不得删除。
- 结论只描述数据支持的范围。
- P4 验收 P2 的扩展数据和 QA，来源抽查必须通过。

### S5：差异样例与故事线

要做：

- 选择 2–3 组最能体现个性化差异的完整输入输出。
- 编写 10 分钟演示脚本，突出检索来源、差异生成、审核驳回和自动修正。
- 为现场 API 失败准备已保存结果和降级演示路径。

通过标准：

- P3 按脚本演示时不超过 10 分钟。
- 每一步都能对应评分点，不展示无关功能。
- P4 验收 P1 的正式界面，确保三类可视化和协同日志可读。

### S6：视频与最终提交

要做：

- 录制 10 分钟以内的最终演示视频。
- 核对代码、数据、评测、部署说明、技术材料和视频是否齐全。
- 使用冻结版本重新走一次完整流程。
- 生成最终提交文件清单和版本号。

通过标准：

- P1 检查视频时长、画面、声音和完整性。
- 视频中的数据和最终提交包完全一致。
- P4 验收 P3 的技术材料，保证任何主张都有代码或评测证据。

## 四、P4 每日检查

- 演示样例是否来自真实可复现的系统输出。
- 页面和视频是否展示失败及修正过程。
- 提示词和实验配置是否保存版本。
- 是否已让验收者运行半成品。
- 验收他人任务时是否抽查了真实数据或实际命令。

## 五、P4 不再长期负责

P4 不再永久承包三层审核、评测和收尾材料。视频是 P4 在 S6 的阶段任务，不代表其他阶段无需参与演示；四个人最终都必须能独立讲清完整数据流。
