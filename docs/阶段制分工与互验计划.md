# 4 人阶段制分工与互验计划（现行）

> 生效日期：2026-07-28  
> 目标提交日：2026-09-05  
> 本文是当前唯一有效的人员分工。`分工_P1_*` 至 `分工_P4_*` 只保留为模块技术参考，不再代表固定人员职责。

## 一、为什么改

产品仍然采用 **1 Orchestrator + 4 Agent** 架构，但产品模块不再等于人员边界。

旧分工让一个人长期承担一个完整领域，容易出现：

- 难度不均：编排集成、数据检索、生成个性化、审核评估的工作量差异很大。
- 单点风险：某人卡住，整条数据流都不能继续。
- 集成过晚：每个人的模块单独能跑，合起来却可能不通。
- 无法互补：成员只熟悉自己的文件，不能接手别人工作。

新分工按阶段完成一条条“可运行、可演示、可验收”的纵向切片。每个阶段 4 人同时开工，阶段末交叉验收，验收通过后全员再进入下一阶段。

## 二、执行规则

### 1. 人员只用 A、B、C、D 标记

A、B、C、D 只是成员标签，不代表长期岗位。每进入一个新阶段，任务和验收对象都会轮换。整段项目中，每个人至少要参与一次 Agent 实现、一次集成或界面、一次测试或数据、一次文档或演示，不能把所有难题永久转给编码最强者。

能力较弱的成员负责高难任务时，先交最小版本，验收者从第一天结对检查；仍不能跑通时再缩小范围或共同完成，但原负责人必须能独立讲清并复现结果。

### 2. 每阶段采用四角互验

验收关系采用三组环并按阶段轮换：

| 轮次 | A 的验收者 | B 的验收者 | C 的验收者 | D 的验收者 |
|---|---|---|---|---|
| R1 | B | C | D | A |
| R2 | C | D | A | B |
| R3 | D | A | B | C |

阶段按 R1 → R2 → R3 循环，避免长期固定搭档。开发者不能给自己的任务判定通过。

验收者从阶段第一天就参与：

- 开工时确认输入、输出和验收样例。
- 开发中使用半成品做接口检查，不等最后一天才看。
- 收尾时必须在自己的电脑或干净环境中复现。

### 3. 每项任务必须交“五件套”

任务没有以下内容，不能算完成：

1. 可运行的代码或数据。
2. 一个正常样例。
3. 一个失败或边界样例。
4. 一条最简运行命令。
5. 验收记录：通过/不通过、发现的问题、修复结果。

### 4. 主分支永远可运行

- 分支按 `s阶段号-成员-任务` 命名，例如 `s2-a-data`。
- 每个任务拆成不超过 1 天的小提交，禁止攒一周再合并。
- 合并前由验收者运行样例；合并后由当阶段值班集成人再跑一次全链路。
- 接口只认 `docs/接口约定.md`，需要修改时必须先更新契约和样例，再改代码。

### 5. 卡住要快速换挡

- 同一问题独立排查超过 2 小时仍无进展，立即把报错、输入和已尝试方法发给验收者。
- 当天仍未解决，由值班集成人把任务缩小、改用 stub 或切换负责人。
- 宁可先做简单可运行版本，也不允许某个“高级功能”阻塞阶段交付。

## 三、阶段总览

| 阶段 | 日期 | 阶段目标 | 退出门槛 |
|---|---|---|---|
| S0 范围与契约 | 7/28–7/29 | 所有人能运行同一套环境，接口和样例冻结 | 4 台电脑环境检查通过；契约样例全员确认 |
| S1 假数据骨架 | 7/30–8/02 | 用 stub 跑通完整闭环 | `streamlit run app.py` 可展示全流程和一次回炉 |
| S2 首条真实链路 | 8/03–8/09 | 跑通“数控机床”黄金场景 | 真实知识可溯源；不同画像生成不同内容 |
| S3 审核与反馈闭环 | 8/10–8/16 | 生成内容能被检查、驳回并自动修正 | 至少 1 个通过案例和 1 个驳回后改善案例 |
| S4 扩展与对比实验 | 8/17–8/23 | 扩展领域、交互功能和异构审核 | 3 个岗位可演示；对比实验可重复 |
| S5 评测与体验 | 8/24–8/29 | 用数据证明效果，完成正式界面 | 核心指标有脚本和原始结果支撑 |
| S6 冻结与提交 | 8/30–9/02 | 完成视频、文档、代码和数据包 | 另一成员可从零部署；10 分钟内演示通过 |
| 缓冲期 | 9/03–9/05 | 只修阻断问题，不新增功能 | 最终提交清单四人签字 |

如果实际进度落后，优先保证 S1、S2、S3、S5 的最小版本；知识图谱美化、复杂 DKT 和额外岗位属于可删减项。

## 四、各阶段四人并行任务

### S0：范围与契约

阶段目标：所有人站在同一起跑线上，先消除“我这里能跑”的环境差异。

| 成员 | 并行任务 | 交付物 | 验收者 |
|---|---|---|---|
| A | 整理主数据流和 Agent 调用顺序 | 一页流程图、`run()` 输入输出样例 | B |
| B | 建最小目录和环境检查清单 | 目录骨架、依赖检查结果、启动命令 | C |
| C | 为每个接口准备正常/异常 JSON 样例 | `tests/fixtures/` 样例和验收表 | D |
| D | 确定首个黄金场景的数据范围 | “数控机床操作”问题清单、来源清单、3 个学员画像 | A |

共同验收：

- 全员逐项朗读并确认 `docs/接口约定.md`。
- 每个人都能在本机运行 Python，并能导入项目依赖。
- 首个黄金场景只聚焦一个可讲清楚的问题，不同时铺开三个行业方向。

### S1：假数据骨架

阶段目标：任何真实算法都可以没有，但完整流程必须先能演示。

| 成员 | 并行任务 | 交付物 | 验收者 |
|---|---|---|---|
| A | 编写检索、画像 stub | `agents/retrieval.py`、`agents/profile.py` | C |
| B | 编写生成、审核、评估 stub | `agents/generator.py`、`agents/reviewer.py`、`agents/evaluator.py` | D |
| C | 编写编排、共享状态、日志和最多 2 次重试 | `orchestrator.py` | A |
| D | 编写最简 Streamlit 页面和冒烟检查 | `app.py`、启动检查表 | B |

共同验收：

- 输入岗位、答题记录和问题后能看到画像、知识、培训内容、审核、评估和协同日志。
- 人为让第一次审核失败时，系统会带修改建议重生成，并在第二次通过。
- 断开任意非关键 API 时，stub 模式仍可演示。

### S2：首条真实链路

阶段目标：只做好“数控机床操作”这一条黄金路径，把 stub 逐段换成真实实现。

| 成员 | 并行任务 | 交付物 | 验收者 |
|---|---|---|---|
| A | 收集、清洗并标注黄金场景知识 | 至少 30 条有来源的 JSON；来源抽查表 | D |
| B | 实现最小真实检索和未覆盖拒答 | 建库脚本、`search_knowledge()`、检索测试 | A |
| C | 实现岗位技能本体和画像更新 | 1 个岗位、6–8 个技能、3 组差异画像 | B |
| D | 实现受知识约束的内容生成 | 生成函数、提示词版本、引用来源校验 | C |

共同验收：

- 检索结果中的每条知识都有可核对来源。
- 知识库未覆盖的问题明确拒答，不能编造答案。
- 同一问题输入三种画像，内容难度、术语解释和任务形式有肉眼可见差异。
- 生成内容引用的来源必须是本次检索结果的子集。

### S3：审核与反馈闭环

阶段目标：完成项目最关键的“发现问题—给出依据—自动修正”闭环。

| 成员 | 并行任务 | 交付物 | 验收者 |
|---|---|---|---|
| A | 实现 L2 知识锚定和幻觉指标 | 逐句核查、事实错误率/无依据率/可溯源率 | B |
| B | 接入驳回、重生成、降级和人工复核状态 | 更新后的 orchestrator、失败注入样例 | C |
| C | 展示协同过程和闭环前后差异 | 审核详情 UI、通过/驳回演示脚本 | D |
| D | 实现 L1 规则检查 | 来源、格式、长度、不确定措辞检查及单测 | A |

共同验收：

- 手工植入一个错误参数，审核必须指出具体句子和依据。
- 修改建议必须能直接指导重生成，不能只写“请修改”。
- 回炉后同一指标有可见改善；连续失败时系统明确标记“需人工复核”。
- 幻觉分数来自实际检查结果，禁止写死为 `0.03`。

### S4：扩展与对比实验

阶段目标：从“单场景能跑”扩展为“足够支撑比赛论证”，但不无限堆功能。

| 成员 | 并行任务 | 交付物 | 验收者 |
|---|---|---|---|
| A | 增加学习路径、降维解释、进阶挑战 | 路径函数、两种交互模式、画像更新样例 | C |
| B | 增加焊接、质量检验两类数据与 QA | 3 个方向共至少 50 组 QA，来源完整 | D |
| C | 接入 L3 三模型投票和故障降级 | 统一模型适配器、2/3 投票、超时降级 | A |
| D | 设计并运行消融与个性化对比实验 | 单次生成 vs 多 Agent、不同画像对比脚本 | B |

共同验收：

- 三家模型中任一家失败时，主流程不崩溃并显示降级状态。
- L3 只在高风险时触发，保留触发原因、耗时和调用次数。
- 三个岗位至少各有一个完整演示样例。
- 对比实验保存输入、配置、原始输出和汇总结果，不能只保留截图。

### S5：评测与体验

阶段目标：把“看起来不错”变成“有证据、可重复、易演示”。

| 成员 | 并行任务 | 交付物 | 验收者 |
|---|---|---|---|
| A | 完成正式界面和三类可视化 | 知识盲区、难度匹配、学习路径、协同日志 | D |
| B | 运行 QA 基准并汇总核心指标 | 评测脚本、原始结果、覆盖率和幻觉率 | A |
| C | 做错误处理、缓存、配置和成本记录 | API 超时/空结果处理、调用统计、配置说明 | B |
| D | 整理差异化样例和演示故事线 | 2–3 组完整输入输出、10 分钟脚本初稿 | C |

共同验收：

- 所有对外数字都能追溯到脚本、测试集和原始输出。
- 界面一次演示能看清“为什么检索、为什么这样生成、为什么通过或驳回”。
- API 超时、检索为空、模型返回非 JSON 三类异常都有可理解提示。
- 第二名成员在不询问作者的情况下能完成一次完整演示。

### S6：冻结与提交

阶段目标：停止扩功能，完成可复现交付。

| 成员 | 并行任务 | 交付物 | 验收者 |
|---|---|---|---|
| A | 冻结代码并做干净环境部署 | 发布候选版本、部署复现记录 | B |
| B | 冻结数据与评测证据 | 数据说明、来源表、评测报告 | C |
| C | 整理技术说明和答辩材料 | 架构、创新点、边界与局限说明 | D |
| D | 录制视频并核对提交清单 | 10 分钟内视频、文件清单、最终包 | A |

共同验收：

- A 的部署由 B 验收，B 的数据由 C 抽查，C 的材料由 D 核对，D 的视频由 A 卡时。
- 四个人各自完整演示一次，任何一人都能解释四个 Agent 的数据流和失败处理。
- 9/03 后只修复阻断运行、数据错误或提交格式问题，不增加新功能。

## 五、每日协作节奏

不需要复杂项目管理工具，每天只做三次短同步：

1. 上午 10 分钟：每人说“今天交什么、输入从哪里来、谁验收”。
2. 下午中途 10 分钟：验收者拿半成品跑一次，尽早暴露接口问题。
3. 晚上 15 分钟：展示可运行结果，记录通过/不通过和明天第一步。

阶段看板只保留四列：

`待做 → 开发中 → 待互验 → 已合并`

任何任务在“开发中”超过 1 天，都必须继续拆小。

## 七、组长职责重新定义

组长不再承包 Orchestrator、界面、集成和视频。组长只负责：

- 维护阶段目标和优先级。
- 主持接口变更确认。
- 确认阶段退出门槛是否满足。
- 在任务阻塞时缩小范围或重新配对。
- 保护主分支可运行。

组长可以开发，但其代码同样必须由另一名成员验收。

## 八、范围取舍

必须完成：

- 可溯源检索和未覆盖拒答。
- 差异化画像与内容生成。
- L1 + L2 审核、驳回重生成闭环。
- 可复现评测、协同过程可视化、异常降级。

有余力再做：

- L3 三模型异构投票。
- 简单知识图谱。
- 仿真学员和消融实验扩展。

时间不足时删除：

- 复杂 DKT 训练。
- 大规模自动知识图谱抽取。
- 与评分无直接关系的界面动画和额外岗位。

原则只有一个：**每个阶段都交付一条更真实、更可靠的完整链路，而不是四个越来越复杂、最后才尝试拼接的孤立模块。**
