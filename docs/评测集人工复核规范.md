# 评测集人工双人复核规范

> 适用数据：`knowledge_base/qa_test_set.json`  
> 当前基线：52 条案例均为“机器初标，待人工双人复核”  
> 原则：AI 和脚本只能准备材料、检查结构，不能冒充标注者或仲裁者填写结论。

## 1. 复核目标与角色

每条案例必须由两名人类标注者独立复核。标注者 A 和标注者 B 检查同一批案例，在双方提交前不得互看结论或讨论答案。出现分歧时，由预先指定且未参与该条初审的人类仲裁者处理。

角色职责：

- 标注者 A：独立核对案例字段、知识绑定、参考答案和原始来源，在所有 A 栏填写结果、日期与本人编号。
- 标注者 B：执行与 A 相同的独立核对，在所有 B 栏填写结果、日期与本人编号。
- 仲裁者：只处理有分歧或被任一标注者判为“无法判断”的案例，查阅原始资料后填写仲裁栏。
- 数据维护者：运行结构校验、合并人工表、按最终人工结论修改评测集；不得替标注者作判断。
- P2 验收者：在另一台电脑复现导出和测试，抽查人工记录能否追溯到原始来源。

## 2. 已核对的真实字段

评测集每条案例当前包含：

`案例ID、问题、岗位、画像组、目标难度、预期知识ID、参考答案、依据来源、来源定位、标注状态`

知识库每条知识当前包含：

`知识ID、内容、来源、来源定位、主题、验证状态、核验日期`

复核时不得擅自重命名以上字段。`预期知识ID` 在 JSON 中是字符串列表；导出到 CSV 后使用 `|` 分隔。

## 3. A、B 必须分别检查的内容

两名标注者各自逐条完成以下四项，填写“是 / 否 / 无法判断”：

1. **问题与岗位匹配**：问题表述明确，适合该岗位；`画像组` 与 `目标难度` 不存在明显冲突。
2. **预期知识 ID 正确**：每个 ID 都存在于 `data/knowledge.json`，且对应内容确实回答问题，不是仅关键词相似。
3. **参考答案正确完整**：答案未超出知识内容，没有增加未经来源支持的数值、步骤、标准号或安全结论；关键限制条件没有丢失。
4. **来源定位有效且支持答案**：定位能到达原文的具体页面、章节或锚点，来源名称与原文一致，定位附近内容直接支持参考答案。

完成四项后，A、B 各自填写：

- `A结论` / `B结论`：`通过`、`需修改` 或 `无法判断`。
- `A修改建议` / `B修改建议`：通过时可留空；其他结论必须写清错误字段、原文依据和建议改法。
- 本人编号与复核日期。不得让 AI、脚本或另一名标注者代填。

## 4. 来源定位核对方法

每条案例按以下顺序核对：

1. 用 `预期知识ID` 在 `data/knowledge.json` 找到对应知识。
2. 比较案例与知识条目的 `依据来源/来源`、`来源定位`，两者应一致。导出脚本会做这一层结构校验。
3. 人工打开 `来源定位`。网页应定位到相关章节；PDF 应定位到明确页码或章节。只打开网站首页不算完成定位。
4. 在原文附近找到能直接支持 `参考答案` 的句子或段落，核对主体、条件、数值、单位、动作和禁止事项。
5. 若链接失效、需要权限、锚点漂移或原文不支持答案，选择“否”或“无法判断”，在修改建议中记录原因。不得凭知识库文本反推“来源应该正确”。

网络暂时不可用时，该条只能暂存为“无法判断”，不能因此改为“已人工复核”。后续应保存新的可定位链接或可靠的文件页码，再重新核对。

## 5. 同意、分歧与仲裁

### 5.1 一致

- A、B 都选择“通过”，四项检查也均为“是”：填写 `一致性结论=同意`，无需仲裁。
- A、B 都认为需要相同修改：也可填写“同意”，但必须先按共同意见修改案例，再由两人核对修改后的最终字段。

### 5.2 分歧

以下任一情况填写 `一致性结论=分歧`：

- A、B 总结论不同；
- 总结论相同，但对知识 ID、答案事实、来源是否支持等关键字段判断不同；
- 任一人选择“无法判断”；
- 两人的修改方案会产生不同最终答案或来源。

`分歧原因` 必须写明：争议字段、A 的判断、B 的判断、各自依据。不能只写“意见不同”。

### 5.3 仲裁

仲裁者独立查看案例、A/B 记录、知识条目和原始来源后填写：

- `仲裁者编号`、`仲裁日期`；
- `仲裁结论`：`通过`、`修改后通过` 或 `退回`；
- `仲裁说明`：最终采用的字段值、原文依据，以及未采用另一意见的原因。

仲裁仍无法确认来源时必须“退回”，不得为了凑数量强行通过。

## 6. 标注状态生命周期

允许的状态只有：

1. `机器初标，待人工双人复核`
2. `人工复核中`
3. `待仲裁`
4. `已人工复核`

`标注状态` 只有满足以下全部条件才允许改为 `已人工复核`：

- 案例 ID 唯一，必填字段和来源定位通过脚本校验；
- A、B 是两名真实人员，均已独立填写本人编号、日期、四项检查和结论；
- 两人一致通过；如存在分歧，已有第三名人类完成仲裁；
- 所有“需修改”均已落实到最终案例，修改后的知识 ID、答案、来源和定位已重新核对；
- 原始来源可定位且直接支持最终参考答案；
- 没有未解决的“否”“无法判断”或空白必填人工栏；
- 数据维护者将最终字段写回 JSON 后，重新运行结构测试并保留复核表。

CSV 的 `最终标注状态` 默认必须为空。导出脚本不会自动写入任何人工结论，也不会修改 JSON。仅由数据维护者根据完整的人类记录人工更新。

## 7. 12 条试标安排

试标选择 3 个岗位各 4 条，覆盖入门、应用、进阶，并包含两条“转岗学习者”复测案例：

| 岗位 | 案例 |
|---|---|
| 数控机床操作工 | QA-001、QA-002、QA-003、QA-040 |
| CNC编程员 | QA-013、QA-014、QA-015、QA-052 |
| 质检员 | QA-030、QA-031、QA-032、QA-039 |

分配方式不是每人各做 6 条，而是：

- 标注者 A 独立复核全部 12 条，只填写 A 栏。
- 标注者 B 独立复核同样 12 条，只填写 B 栏。
- 两份填写结果都提交后再合并和比较，避免相互暗示。
- 有分歧的条目交给未参与该条初审的人类仲裁者。

空白试标表保存于 `data/review/qa_pilot_12_review.csv`。该表只含机器初标内容，所有 A/B、分歧和仲裁字段均为空。

## 8. 运行命令

Windows PowerShell：

```powershell
.\venv\Scripts\Activate.ps1
python knowledge_base/export_review_csv.py `
  --case-id QA-001 --case-id QA-002 --case-id QA-003 --case-id QA-040 `
  --case-id QA-013 --case-id QA-014 --case-id QA-015 --case-id QA-052 `
  --case-id QA-030 --case-id QA-031 --case-id QA-032 --case-id QA-039
python -m pytest -q tests/test_review_export.py
```

导出命令会先检查全部 52 条案例；存在重复案例 ID、缺少来源定位、非法状态或知识来源绑定不一致时，不生成复核表并以非零退出码失败。

## 9. 正常与分歧填写示例

以下仅说明填写格式，不是对真实案例的人工结论，不能写入正式复核表。

正常格式示例：

```text
标注者A编号=成员甲，A四项检查=是，A结论=通过
标注者B编号=成员乙，B四项检查=是，B结论=通过
一致性结论=同意，分歧原因留空，仲裁栏留空
```

分歧格式示例：

```text
A结论=通过
B结论=需修改
一致性结论=分歧
分歧原因=B认为参考答案遗漏原文中的适用条件；A认为不影响核心结论。
仲裁结论=修改后通过
仲裁说明=补入适用条件，并由 A、B 重新核对修改后的答案和来源。
```

## 10. 记录保存与验收

- 保留未填写的原始 CSV、A 的独立副本、B 的独立副本、合并后的复核表和仲裁记录。
- 不覆盖原始填写记录；修订版使用日期或版本号区分。
- 复核表含人员编号和日期，不应包含 API Key、口令或其他无关敏感信息。
- 正式评测只能使用 JSON 中状态为 `已人工复核` 的案例；试标表、机器初标和离线诊断不得作为正式竞赛指标。

P2 验收时应实际运行导出命令与测试，检查正常导出、三类安全失败、人工栏全空，以及任意抽取案例能否从 CSV 追溯到知识库和原始来源。
