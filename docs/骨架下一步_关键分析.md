# 骨架下一步：最该补什么 & 最棘手的是什么

> 当前骨架状态（2026-07-18）：5 个 Agent stub + orchestrator + Streamlit 全链路跑通，但全部返回硬编码假数据。
> 本文分析从骨架到可演示系统之间，**最优先补什么、最棘手的坑在哪**。

---

## 一、当前最需要补的（按紧迫性排序）

### 第 1 优先：`.env` + 统一 LLM 调用层

**现状**：项目完全没有调用任何 LLM API。`generator.py` 返回硬编码模板，`reviewer.py` 用 `random.random()` 模拟投票。

**需要做的**：
- 封装一个统一的 `call_llm(prompt, model)` 函数，屏蔽 3 家厂商的 base_url 差异
- `.env` 填好 3 家 API key，调通至少一家
- 先不追求三模型投票，**能调通一家就算突破**

**为什么最优先**：没有 LLM，后面所有'智能'都是假的，骨架永远只是骨架。

---

### 第 2 优先：`generator.py` 接入真实 LLM

**现状**：`generate_content()` 从 `_MOCK_TRAININGS` 字典里按岗位挑模板。

**需要做的**：
- 把 prompt 写好：给 LLM 喂画像（弱项技能）+ 知识列表（只能基于这些知识生成）+ 内容类型要求
- prompt 里加硬约束：「只能基于以下知识生成，不得编造知识中没有的事实」「来源必须标注」
- 输出格式化为 JSON（类型/标题/正文/引用来源）

**提示词设计要点**：
```
你是制造业培训专家。请根据以下学习者画像和知识库内容，生成一份个性化培训教程。

【学习者画像】
- 岗位：{岗位}
- 弱项技能：{技能A}(掌握度{0.3})、{技能B}(掌握度{0.4})
- 强项技能：{技能C}(掌握度{0.8})

【可用知识库】（你只能基于以下内容生成，不得编造）
{知识1}（来源：xxx）
{知识2}（来源：xxx）

【要求】
1. 针对弱项技能重点展开
2. 每条断言必须对应知识库中的某一条
3. 输出 JSON 格式：{"类型":"教程", "标题":"...", "正文":"...", "引用来源":[...]}
```

---

### 第 3 优先：`retrieval.py` 接入 ChromaDB

**现状**：`search_knowledge()` 在内存里用关键词匹配 7 条假知识。

**需要做的**：
- 把 `_MOCK_KNOWLEDGE` 写入 ChromaDB（`knowledge_base/build_chromadb.py`）
- `retrieval.py` 里用 ChromaDB 的 `query()` 做语义检索
- 保留来源字段（这是审核锚定的依据）

**注意**：ChromaDB 是本地向量库，不需要额外服务。stub 里的 7 条数据够做 Demo，真实数据由 P2 后续补充。

---

### 第 4 优先：`profile.py` 画像逻辑细化

**现状**：3 个岗位 × 7 项技能的静态先验表，答题记录只做 ±0.05 的简单加减。

**需要做的**：
- 技能间的**先修关系**（比如「切削参数选择」是「缺陷识别」的先修，前者不掌握后者不可能高分）
- 答题记录不只二元对错，加**置信度**（连续答对 3 次 > 答对 1 次）
- 冷启动时用 LLM 根据岗位描述推理技能先验（比人工写死的表更灵活）

---

### 第 5 优先：`evaluator.py` 评估逻辑细化

**现状**：用关键词计数算专业性、用 Markdown 符号算可读性——太粗糙。

**需要做的**：
- 事实性 → 调 LLM 逐句比对知识库（或者直接用审核层的锚定分数）
- 专业性 → LLM 判断术语使用是否规范
- 匹配度 → 覆盖了哪些弱项技能、难度是否合适

---

## 二、最关键且最棘手的部分

### 棘手 #1：三模型异构投票怎么落地

**为什么关键**：这是全组的王牌创新点（反幻觉），也是赛题「多智能体协同」的核心体现。

**为什么棘手**：

| 问题 | 难度 |
|------|------|
| **成本**：每条内容跑 3 个不同厂商模型，一次生成 + 审核 = 4 次 API 调用（1 生成 + 3 投票），贵且慢 | 工程优化 |
| **裁决机制**：简单多数？加权？锚定说「通过」但 3 个模型都说「不通过」听谁的？ | 设计决策 |
| **幻觉评判标准**：3 个模型怎么判断一段文本有没有幻觉？prompt 怎么设计才能让模型做可靠的事实核查？ | 提示词工程 |
| **不可复现**：同一个内容跑两次投票可能结果不同（LLM 的随机性），怎么保证审核结果的稳定性？ | 根本性难题 |

**建议的分级策略**（研究方案里提到的）：

```
规则引擎不通过 → 直接打回，不走后续
规则通过 + 锚定 ≥ 0.8 → 快速通道，只调 1 个模型复核
规则通过 + 锚定 < 0.8 → 升级到三模型投票
```

这样大部分常规内容走快速通道，只有高风险内容才触发昂贵的三模型投票。**这本身就是一个创新点（自适应审核强度）。**

---

### 棘手 #2：幻觉评测基准 —— "5% 以下"怎么证明

**为什么关键**：评委一定追问「你说幻觉率 < 5%，怎么测的？」没有可信基准，这个数字就站不住。

**为什么棘手**：

- 没有现成的「制造业培训内容事实核查数据集」
- 自己构造需要 domain expert 标注，但团队没有制造业专家
- 即使构造了，标注本身就是主观的（什么叫事实错误？）

**建议方案**（把「如何度量幻觉」本身做成研究贡献）：

1. 从假知识库的 7 条知识出发，**人为构造** 20 条「含幻觉的培训内容」（故意编造、张冠李戴、数据错误）
2. 用三层审核去检测，计算检出率 = 检出的幻觉数 / 构造的幻觉总数
3. 定义可复现指标：事实性错误率、无依据陈述率、可溯源率
4. 文档诚实说明「基于自建测试集的评测」，不自称权威基准

---

### 棘手 #3：动态编排的必要性证明

**为什么关键**：大量队伍只做「顺序调用 4 个 prompt」。你们要证明「多智能体协同 > 单体大 prompt」。

**为什么棘手**：

- 需要做**消融实验**：同样的输入，分别跑 (A) 单体大 prompt 一次生成 v.s. (B) 多 Agent 协同，对比质量
- 消融实验的结果必须可量化（用 evaluator 打分对比）
- orchestrator 的动态决策（审核不通过 → 带建议回炉 → 再审核）vs 静态流水线，需要用数据证明动态更好

**建议**：在 orchestrator 里记录每次重试前后 evaluator 分数的变化，Demo 里展示「重试让综合分从 0.6 提升到 0.85」——这就是动态优化的可视化证据。

---

### 棘手 #4：个性化冷启动 —— 没有真实学员数据

**为什么关键**：个性化占 20 分，但没有制造业员工答题数据，DKT 无从训练。

**为什么棘手**：

- DKT 需要大量学员交互序列来训练
- 用 LLM 模拟学员可以造数据，但评委可能质疑「你用 AI 模拟的人来验证 AI 生成的培训？」

**建议方案**（研究方案里提到的）：

1. 弱化「DKT」标签，强化「岗位画像 + 知识状态」双驱动
2. 冷启动用岗位能力模型（已完成 stub）
3. 少量答题后快速更新（stub 已有简单逻辑，后续可换贝叶斯知识追踪 BKT——比 DKT 简单且可解释）
4. Demo 里演示 2-3 组差异化学习者画像（新手 v.s. 老手 v.s. 转岗），展示系统对不同画像生成不同内容

---

## 三、一句话总结

| 维度 | 答案 |
|------|------|
| **最优先补** | 统一 LLM 调用层 → generator 接入真实 LLM → retrieval 接入 ChromaDB |
| **最关键** | 三模型异构投票（王牌创新，但成本 + 裁决机制 + 稳定性都要解决） |
| **最棘手** | 幻觉评测基准（没有现成数据集，要自己构造且能被评委认可） |
| **最容易忽视** | 动态编排的消融实验（证明多 Agent > 单体，否则架构选择站不住脚） |

> **下一步行动建议**：P1 先把 `.env` 配好 + 封装统一 LLM 调用 → P3 用真实 LLM 替换 generator → P4 至少接一家模型做单模型事实核查 → 全组跑通一条「真实 LLM 生成 + 真实 LLM 审核」的链路。这一步跨出去，骨架就变成系统了。
