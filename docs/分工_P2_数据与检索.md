## 三、各阶段怎样才算完成

### S0：目录与环境

要做：

- 建立 `agents/`、`knowledge_base/`、`data/`、`tests/fixtures/` 等最小目录。
- 核对 Python、依赖、`.env.example` 和启动命令。
- 整理 Windows 与 macOS 的最小差异。

通过标准：

- P3 能在自己的电脑完成安装检查。
- 不需要真实 API key 也能运行基础检查。
- P2 验收 P1 的数据流图与 `run()` 样例，重点检查字段是否完整。

### S1：生成、审核、评估 stub

要做：

- `generate_content()` 返回类型、标题、正文和引用来源。
- `review_content()` 能按测试开关返回一次失败、下一次通过。
- `evaluate()` 返回五项评分和优化建议。

通过标准：

- P4 可直接导入所有函数。
- stub 返回值严格符合接口约定。
- P2 验收 P4 的最简页面：能输入、运行并展示完整结果。

### S2：真实检索

要做：

- 读取 P1 的真实知识 JSON 并建立最小可用索引。
- `search_knowledge()` 返回带来源的 top-3。
- 相似度低或知识库未覆盖时返回明确拒答状态。

通过标准：

- P1 的覆盖问题能命中正确来源。
- 未覆盖问题不能返回看似合理的编造内容。
- 相同输入重复运行时输出结构稳定。
- P2 验收 P3 的画像：冷启动和有答题记录两种情况都能运行。

### S3：闭环编排

要做：

- 将 L1、L2 的审核结果接入 orchestrator。
- 审核不通过时，把具体修改建议传回生成函数。
- 最多重试 2 次；继续失败则标记“需人工复核”。
- 保存每次尝试的协同日志和指标变化。

通过标准：

- P3 能复现一次“失败 → 重生成 → 通过”。
- API 或审核异常时不会无限循环。
- P2 验收 P1 的 L2，检查修改建议是否具体、指标是否可重复。

### S4：扩展数据与 QA

要做：

- 在数控场景之外增加焊接和质量检验数据。
- 将 QA 扩展到至少 50 组，每组带参考答案和依据来源。
- 至少 20 组包含可核验的数字、步骤或标准号。

通过标准：

- P4 随机抽查来源时能定位原文。
- 测试集覆盖三个岗位，不重复改写同一问题凑数量。
- P2 验收 P4 的实验：输入、配置、原始输出和汇总结果齐全。

### S5：评测基准

要做：

- 批量运行 QA 测试集。
- 汇总覆盖率、拒答正确率、幻觉率、个性化匹配度和 L3 触发率。
- 保存每条样例原始输入输出，不只保存平均值。

通过标准：

- P1 可从原始记录重新计算汇总数字。
- 失败样例没有被删除，并有原因分类。
- P2 验收 P3 的健壮性：超时、空检索、非 JSON 返回都有处理。

### S6：数据与证据冻结

要做：

- 冻结最终数据版本、QA 版本和评测配置。
- 写清数据来源、处理过程、使用范围和已知局限。
- 生成最终评测报告和供答辩使用的指标表。

通过标准：

- P3 可将报告中的每个指标追溯到原始结果。
- 数据版本与视频演示使用的版本一致。
- P2 验收 P1 的发布候选版本，按部署说明从零启动。

## 四、P2 每日检查

- 输出格式是否与接口约定一致。
- 数据来源是否真实存在且能定位。
- 评测是否保存失败样例和原始记录。
- 当日是否已经让验收者运行半成品。
- 自己负责验收的任务是否实际执行过命令。

## 五、P2 不再长期负责

P2 不再永久承包数据收集、ChromaDB、知识图谱和检索。完成本阶段任务后，下一阶段按新任务切换，相关知识必须通过样例、说明和验收记录交给全组。
