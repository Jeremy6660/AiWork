# 12 条人工双人复核 · 操作指南

> 配套文档：判断标准以 `docs/评测集人工复核规范.md` 为准，本文是它的**操作化手册**。
> 适用范围：`data/review/qa_pilot_12_review.csv` 的 12 条试标案例。
> 更新日期：2026-08-05
> 目标读者：标注者 A、标注者 B、仲裁者、数据维护者、P2 验收者。

---

## 0. 一句话流程

**两名真人各自独立复核全部 12 条 → 各自填 A 栏 / B 栏 → 合并比较 → 有分歧交第三名真人仲裁 → 数据维护者写回 JSON 并跑测试 → 交接 P2 独立验收。**

全程只有两个硬规则：
1. **A、B 提交前不得互看、不得讨论**（防互相暗示）。
2. **AI / 脚本 / 另一方都不能代填任何人工结论**（违反即 E1 不通过）。

预计耗时：每人 2~3 小时（12 条 × 10~15 分钟）。

## 1. 角色与分工

| 角色 | 人数 | 做什么 | 红线 |
|---|---|---|---|
| 标注者 A | 1 名真人 | 独立复核**全部 12 条**，只填 A 栏 | 提交前不看 B 的结论 |
| 标注者 B | 1 名真人 | 独立复核**全部 12 条**，只填 B 栏 | 提交前不看 A 的结论 |
| 仲裁者 | 1 名真人（未参与初审） | 只处理分歧或"无法判断"的条 | 查原始资料后独立判断 |
| 数据维护者 | 1 名真人 | 合并表、校验结构、写回 JSON | **不得替标注者作判断** |
| P2 验收者 | 1 名真人（另一台电脑） | 复现导出/测试，抽查溯源 | 实际执行命令，不看截图定结论 |

注意：**不是"每人各做 6 条"**，是每人独立做**全部 12 条**。

## 3. 第 1 步：标注者逐条审核的标准动作（每人 12 条 × 10~15 分钟）

对每一条案例，按固定顺序做 5 个动作：

### 动作 1：读题（1 分钟）
看 CSV 行的前 9 列：`问题`、`岗位`、`画像组`、`目标难度`、`预期知识ID`、`参考答案`、`依据来源`、`来源定位`。
心里先有个判断：这题问的是什么？画像组（P1 入门 / P2 应用 / P3 进阶）和难度是否协调？

### 动作 2：查知识（1 分钟）
在 `data/knowledge.json` 中按 `预期知识ID` 找到知识条目，读它的 `内容` 和 `来源定位`。
**比对两处**：
- 案例的 `依据来源` ≈ 知识的 `来源`？
- 案例的 `来源定位` ≈ 知识的 `来源定位`？

### 动作 3：开原文（3 分钟）
浏览器打开 `来源定位`，**必须到达具体章节/锚点**（只打开网站首页不算完成定位）。
网页看锚点章节，PDF 看页码。

### 动作 4：核对（5 分钟）
在原文附近找到**直接支持参考答案的句子**，逐词核对：主体、条件、数值、单位、动作、禁止事项。
重点问自己三个问题：
1. 原文真的说了这个意思吗？（不是知识库文本反推"来源应该正确"）
2. 参考答案有没有**超出原文**的内容（多出来的数值、步骤、标准号、安全结论）？
3. 参考答案有没有**丢关键条件**（如"运行期间""断电后"这类限定）？

### 动作 5：填表（1~2 分钟）
在**自己那份 CSV** 填：4 项检查 → 结论 → 修改建议（如需）→ 本人编号 + 日期。
填完一条做下一条。**全部 12 条填完前，不回头看已填的结论，不与他人讨论。**

## 5. 第 3 步：判定标准与字段填写规范

### 5.1 四项检查（每项填：`是` / `否` / `无法判断`）

| 检查项 | 填"是"的条件 | 典型"否"场景 |
|---|---|---|
| 问题与岗位匹配 | 问题明确、适合该岗位；画像组与难度无明显冲突 | 入门难度配进阶画像；问题与岗位无关 |
| 预期知识ID正确 | ID 存在于 knowledge.json，且内容真能回答该问题 | ID 不存在；内容只是关键词沾边 |
| 参考答案正确完整 | 未超出知识内容；无额外数值/步骤/标准号/安全结论；关键条件没丢 | 答案多了原文没有的内容；漏了适用条件 |
| 来源定位有效且支持答案 | 定位到达具体章节/锚点；附近内容直接支持答案 | 链接失效/需权限/锚点漂移/原文不支持 |

### 5.2 总结论（填：`通过` / `需修改` / `无法判断`）

- **通过**：四项全"是"。
- **需修改**：至少一项"否"，或认为案例本身要改（改字段、改答案、改来源）。**必须写清修改建议**。
- **无法判断**：网络不可用、来源打不开、原文含糊到无法定论。**只能暂存，不能因此算"已人工复核"**。

### 5.3 修改建议的写法（"需修改"时必填）

格式：`错误字段 + 原文依据 + 建议改法`。示例：
> 来源定位无效：防护窗内容在原文 `#Machine Enclosure and Safety Glass inspection` 章节，`#3.2` 定位不到；建议改为对应锚点后重新核对。

禁止只写"感觉不对""建议改一下"。

### 5.4 编号与日期

`标注者A编号` / `标注者B编号` 填本人编号（如 成员甲/成员乙，或组内约定的代号），`A复核日期` / `B复核日期` 填当天日期。**本人编号和日期必须自己填**。

## 6. 第 4 步：合并、比较与分歧判定（数据维护者做）

1. A、B 都交回后，把两份内容**合并进主表** `qa_pilot_12_review.csv`（原始空白副本保留存档）。
2. 逐条比较 A、B 的 4 项检查和结论，填 `一致性结论`：

| 情况 | 一致性结论 |
|---|---|
| A、B 都"通过"且四项全"是" | `同意`（无需仲裁） |
| A、B 结论不同 / 关键字段判断不同 / 任一人"无法判断" / 修改方案会产生不同最终答案 | `分歧` |
| A、B 都要求相同修改 | 也可 `同意`，但必须先改案例、再让两人核对修改后字段 |

3. 填 `分歧原因`（只写"意见不同"不算数），格式：
   > 争议字段 + A 的判断 + B 的判断 + 各自依据。
   示例：`预期知识ID：A 认为 CNC-SAFE-003 内容匹配防护窗；B 认为 QA-003 答案超出该知识范围，原文锚点不支持。`

---

## 7. 第 5 步：仲裁（仲裁者做）

只处理标记为 `分歧` 或 `无法判断` 的条目：

1. 独立查看：案例字段、A/B 两份记录、知识条目、原始来源。
2. 填写：`仲裁者编号`、`仲裁日期`、`仲裁结论`（`通过` / `修改后通过` / `退回`）、`仲裁说明`。
3. `仲裁说明` 必须写：最终采用的字段值 + 原文依据 + **未采用另一意见的原因**。
4. **仲裁仍无法确认来源时必须"退回"**，不得为了凑数量强行通过。

---

## 8. 第 6 步：最终状态判定（数据维护者做）

`最终标注状态` **默认必须为空**。只有**同时满足以下全部条件**，才允许改为 `已人工复核`：

- [ ] 案例 ID 唯一，必填字段和来源定位通过脚本校验
- [ ] A、B 是两名真实人员，均已独立填写编号、日期、四项检查、结论
- [ ] 两人一致通过；有分歧的已有第三名人类完成仲裁
- [ ] 所有"需修改"已落实到最终案例，修改后的知识 ID、答案、来源、定位已重新核对
- [ ] 原始来源可定位且直接支持最终参考答案
- [ ] 没有未解决的"否""无法判断"或空白必填人工栏
- [ ] 数据维护者把最终字段写回 JSON 后，重新跑结构测试并保留复核表

**只有这一栏的判定者是数据维护者本人，且依据的是上面的真人记录。**

## 9. 第 7 步：收尾（数据维护者做）

1. 运行结构测试与全量测试：
   ```powershell
   python -m pytest -q tests/test_review_export.py
   python -m pytest -q
   ```
   期望：结构测试通过，全量 68 passed。
2. 若 12 条全部满足第 8 节条件，把 `knowledge_base/qa_test_set.json` 中对应案例的 `标注状态` 由 `机器初标，待人工双人复核` 改为 `已人工复核`（**只改这一处，其余字段按复核结果同步**）。
3. 保存证据（**不覆盖原始记录，修订版用日期/版本号区分**）：
   - 原始空白 CSV（存档）
   - A 的独立副本、B 的独立副本
   - 合并后的复核表（含一致性结论）
   - 仲裁记录（仲裁表或单独 md）
   - 测试命令输出（退出码）
   - git 提交记录（提交号）
4. 建议当天提交：`git add -A && git commit`（按组内约定提交，不擅自新建分支）。

## 10. 第 8 步：交接 P2 独立验收

给 P2 的验收清单应包含：
- [ ] A、B、仲裁者编号及各自复核/仲裁日期
- [ ] 12 条逐项状态（通过/需修改/无法判断/仲裁结果）
- [ ] 分歧条目清单与处理结果
- [ ] 实际运行命令与退出码（结构测试、全量 pytest）
- [ ] 写回 JSON 的变更明细
- [ ] 证据文件路径（原始表、A/B 副本、合并表、仲裁记录）

P2 验收要点（对照 `docs/当前状态与下一步执行方案.md` 第十一节）：
- 核对 A/B 是两名真人、人工栏完整、来源可定位、分歧有仲裁
- 抽查至少 3 条能从 CSV 追溯到知识库和原始来源
- 只对**已提交**代码执行命令，输出"实际命令 + 退出码"

## 11. 红线与常见错误（翻车清单）

| # | 常见错误 | 正确做法 |
|---|---|---|
| 1 | 不打开链接，看知识库文本就判"来源应该正确" | **必须打开原文**核对，找不到支持句就"否/无法判断" |
| 2 | 没发现多条案例复用同一链接/锚点漂移 | 对照第 4 节表格，逐条确认锚点真实覆盖该问题 |
| 3 | 修改建议写"感觉不对" | 必须：错误字段 + 原文依据 + 建议改法 |
| 4 | 网络不通时标"否"或"通过" | 只能 `无法判断` 暂存，网络恢复后再核 |
| 5 | A、B 讨论后填写 / 一方替另一方填 | 独立填写，提交前互不看 |
| 6 | 让 AI 或脚本填结论、签字 | 人工栏全部真人填写 |
| 7 | 把机器初标 / 试标表结果当正式竞赛指标 | 正式评测只用 JSON 中 `已人工复核` 的案例 |
| 8 | 为凑数量把无法确认的条强行"通过" | 如实 `无法判断` / `退回` |
